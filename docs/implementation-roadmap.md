# Implementation Roadmap

## Purpose

Blueprint Engine will become a small, dependable TypeScript package for applications with configurable domain workflows. A blueprint declares an input contract once; the server can publish a rendering schema and validate submitted input from that same contract.

The goal is not to replace front-end form libraries, JSON Schema, validation libraries, ORMs, or authorization systems. The goal is to remove product- and tenant-specific branching from shared application code when the same variability appears across more than one flow.

## Product Thesis

An application should be able to add a new product flow by adding a DTO, its tests, and an application-owned policy entry. It should not need to change the engine, duplicate a page, or add branches throughout unrelated controllers and services.

The core contract is:

```text
Blueprint DTO -> schemaFor() -> client renderer
Client input  -> parse()     -> validated application command
```

Tenant, actor, product, and authorization policy stay in the host application. The core package must remain unaware of databases, HTTP frameworks, UI frameworks, and proprietary domain entities.

## Milestone Map

Milestones are evidence gates, not calendar promises. A milestone is complete only when its acceptance criteria pass in a clean clone and its artifact is visible to a prospective adopter.

| Milestone | Outcome | Depends on | Public artifact |
|---|---|---|---|
| M0 | Small dependency-free core | None | Source, tests, README |
| M1 | Runnable Cake Shop demonstration | M0 | Example API and web client |
| M2 | Stable, documented schema contract | M1 | Schema specification and fixtures |
| M3 | Proof across two domains | M2 | Second runnable example and comparison |
| M4 | Safe context/policy integration guidance | M3 | Catalog and authorization example |
| M5 | Installable public prerelease | M4 | npm `0.x`, CI, governance files |
| M6 | Stable core release | M5 plus real adoption | `1.0.0` release and migration policy |

The following sections define the scope of each milestone. No work from a later milestone is required to complete an earlier one.

### M0: Foundation (complete)

**Goal:** demonstrate a small, runnable core.

Deliverables:

- `@Field` for primitive inputs.
- `@Nested` for reusable nested DTOs.
- Deterministic schema generation with `schemaFor`.
- Server-side hydration and validation with `parse`.
- Tests for nested schema generation and invalid submitted input.
- README, MIT license, and a clear statement of non-goals.

Exit criteria:

- `npm test` passes from a clean clone after `npm install`.
- The Cake Shop example can explain the API without proprietary code.
- The core has no runtime dependency outside Node and TypeScript output.

Checklist:

- [x] Initialize an independent Git repository.
- [x] Implement field metadata, nesting, schema generation, and parsing.
- [x] Add contract tests for a nested DTO and server-side validation.
- [x] Write the README, development context, license, and roadmap.
- [x] Make the initial commit.

### M1: End-to-End Cake Shop Demonstration (complete)

**Goal:** prove the core works in a real request/response loop.

Build one runnable example application, not a generic demo platform:

- A small API exposes a selected blueprint schema.
- A minimal web client renders `text`, `number`, `select`, `boolean`, `upload`, and nested fields.
- The client submits data to the API.
- The API returns structured validation errors from `parse`.
- The UI maps errors to field paths, including nested paths.

Use the Cake Shop domain:

- `BirthdayCake` has message, tiers, topping, and optional image upload metadata.
- `NakedCake` has fruit selection and tiers.
- A host-owned catalog maps a product key to an allowed DTO.

Do not add a visual page builder, database, authentication, tenant administration panel, or a built-in HTTP framework integration in this phase.

Exit criteria:

- A developer can run the example in under five minutes.
- A visitor can see two different forms generated by the same engine.
- A manipulated client payload is rejected by the server.

Implementation slices:

1. Add `examples/cake-shop/api` with a single in-memory catalog and two DTOs.
2. Add `examples/cake-shop/web` with one renderer for the components already supported by the core.
3. Add one schema endpoint and one submit endpoint; keep both handlers application code.
4. Add an end-to-end test that submits valid and invalid payloads.
5. Add exact run instructions to the README; record a short GIF or video before the first public announcement.

Out of scope: tenant persistence, uploads, user accounts, a configurable catalog UI, and framework adapters.

### M2: Schema Contract Hardening

**Goal:** make the schema a deliberate public contract rather than an implementation detail.

Deliverables:

- Add a `schemaVersion` field to every generated schema.
- Document every schema field, component type, validation rule, and error shape.
- Add fixtures for every supported component and validation result.
- Define backwards-compatibility rules and semantic versioning policy.
- Test inheritance and definition overrides, nested error paths, empty optional values, and invalid root input.
- Decide whether the public schema remains Blueprint Schema or needs a one-way adapter to JSON Schema.

Decision rule:

- Keep Blueprint Schema as the primary contract while its renderer needs are small.
- Add a JSON Schema adapter only when an adopter has a concrete interoperability need.
- Do not claim JSON Schema compliance unless the generated result actually follows that specification.

Exit criteria:

- A schema consumer can be implemented from the documentation alone.
- Breaking schema changes are detectable in tests and release notes.

Implementation slices:

1. Write `docs/schema-specification.md` with one example per component.
2. Add `schemaVersion` and assert it in every schema contract test.
3. Add fixtures for valid schema output and invalid input error output.
4. Add tests for optional fields, invalid root input, nested error paths, inheritance overrides, and unknown input policy.
5. Decide and document whether unknown input keys are rejected or ignored; make the parser follow that decision consistently.

Decision checkpoint: do not add JSON Schema compatibility unless M1 or an adopter proves that another renderer needs it.

### M3: Second Domain Validation

**Goal:** verify that the abstraction is not specific to cakes or a single SaaS.

Create a second example from a distinct domain, such as supplier onboarding, service request intake, or loan eligibility. It must include a nested DTO and at least one product-specific constraint.

Measure the comparison:

| Question | Evidence to collect |
|---|---|
| Does a new flow modify core code? | Git diff for a new DTO and catalog entry |
| Can one client render both flows? | Screenshot or recorded demo |
| Is the server still authoritative? | Invalid payload test |
| Is reuse real? | Shared nested DTO used by both flows |

Exit criteria:

- Two unrelated domains use the same public API without special cases in the core.
- Any feature requested by only one example remains application code.

Implementation slices:

1. Choose one domain that is not commerce: supplier onboarding, public service intake, or eligibility assessment.
2. Build the example using the exact M2 core API, without new decorators.
3. Share at least one nested-contract pattern with the Cake Shop example.
4. Add a comparison page showing the files changed to add a blueprint versus a hard-coded flow.
5. Open issues for pain points instead of immediately adding features.

Decision checkpoint: if the examples need incompatible abstractions, narrow the package's promise instead of adding a broad plugin system.

### M4: Context and Policy Guidance

**Goal:** make multi-tenant use safe without coupling tenants to the engine.

Deliverables:

- A documented host-application catalog example: `context -> allowed blueprint`.
- A security note: never accept a client-selected blueprint without server-side policy validation.
- Optional interfaces or helper functions only if the two example applications duplicate the same code.
- A clear distinction between tenant configuration and a DDD bounded context.

The package must not contain a database-backed tenant registry, roles, authentication, or product entitlement implementation.

Exit criteria:

- Documentation shows policy resolution before both `schemaFor` and `parse`.
- No example trusts a product or blueprint key supplied by an unauthorized client.

Implementation slices:

1. Add `docs/context-policy.md` with an allow-list catalog example.
2. Update both example APIs to resolve the selected blueprint from authenticated or server-owned context.
3. Add a regression test proving a disallowed product key cannot be parsed.
4. Extract a helper only when both examples contain the same policy boilerplate.

Out of scope: identity providers, RBAC, tenant database schemas, and entitlement billing.

### M5: Public Prerelease Readiness

**Goal:** make the package safe to adopt and easy to evaluate.

Deliverables:

- Confirm the final npm package name and scope availability.
- Configure package metadata: repository URL, bugs URL, homepage, keywords, author/contributors, and `publishConfig`.
- Produce only `dist/` in the npm tarball and inspect it with `npm pack --dry-run`.
- Add a CI workflow for install, build, test, and package inspection.
- Add `CHANGELOG.md`, `CONTRIBUTING.md`, issue templates, pull request template, and a code of conduct.
- Publish `0.x` prereleases only after the examples and documentation are reproducible.

Release policy:

- `0.x`: API may change; document migration notes for every breaking change.
- `1.0`: only after at least one independent adopter or production pilot validates the API.
- Keep the core dependency-free unless a dependency removes meaningful maintenance risk.

Exit criteria:

- A fresh external project can install, import, build, and execute the documented quick start.
- CI is required for changes to source and package metadata.

Implementation slices:

1. Reserve or confirm the npm scope and repository name before documentation refers to them as final.
2. Add GitHub Actions for Node LTS install, build, test, and `npm pack --dry-run`.
3. Add package metadata and verify the packed tarball contains only intended published files.
4. Add governance files and issue templates with a minimal contribution workflow.
5. Publish an explicitly experimental `0.1.0` package only after the quick start is tested from a new directory.

Release gate: a contributor who has never seen the repository must be able to follow the README without copying source files from the examples.

### M6: Stable Core Release

**Goal:** stabilize the core only after external or production evidence confirms its boundary.

Required evidence:

- One production pilot or independent external adopter.
- Two distinct domains using the core without forks.
- No unresolved critical issue in schema compatibility, validation correctness, or package installation.
- A documented migration path from the final `0.x` release.

Deliverables:

- `CHANGELOG.md` with the `1.0.0` compatibility promise.
- Final API and schema documentation.
- A release checklist that verifies examples, tarball contents, tests, and versioning.
- A public issue/discussion describing why the API is considered stable.

### Post-M6: Ecosystem, Only When Earned

**Goal:** add integrations in response to demonstrated adoption.

Possible optional packages:

- `@blueprint-engine/express` for thin route helpers.
- `@blueprint-engine/react` for a reference renderer.
- `@blueprint-engine/json-schema` for a documented adapter.

Each adapter must be independently installable. The core must not import them.

Do not create an adapter because a framework is popular. Create it when an adopter has a tested integration need that cannot remain a short example.

## Backlog Rules

Create an issue for every proposed feature and assign it to one of these buckets before implementation:

| Bucket | Rule | Examples |
|---|---|---|
| Core now | Required by M0-M2 and reusable by all DTOs | validation errors, schema versioning |
| Example only | Needed to demonstrate a domain but not reusable yet | Cake Shop product selector |
| Candidate | Needed by two independent domains; requires an API proposal | conditional visibility, cross-field rules |
| Rejected for now | Expands the package beyond its thesis | ORM, page builder, auth, database catalog |

A candidate becomes core only after a short design issue defines the user problem, two example uses, API shape, failure behavior, and test cases. This is the guardrail against decorators and options growing faster than real adoption.

## Engineering Standards

### API Design

- Prefer a small explicit API over decorator variants and configuration flags.
- Preserve server-side validation at every trust boundary.
- Return structured errors with stable field paths.
- Keep schemas deterministic: the same DTO must generate the same output.
- Treat a schema key, component meaning, and error shape as a compatibility commitment.

### Testing

The minimum test suite must cover:

- Every primitive component and validation option.
- Required and optional fields.
- Nested DTOs, nested error paths, and inheritance overrides.
- Unknown and malformed root input.
- Schema snapshots or exact contract assertions.
- The end-to-end example request/response path.

### Security

- Never trust client-selected blueprints or schemas as an authorization decision.
- Parse and validate every submitted payload on the server.
- Define upload fields as metadata or references; do not make the core upload files.
- Avoid arbitrary class loading or evaluation from a blueprint key.
- Review public examples for accidental tenant, customer, or production data.

## Adoption and Communication Plan

The project earns interest through proof, not claims.

1. Publish a two-minute demo of the Cake Shop example.
2. Publish the article that explains the "second customer" problem and link directly to the runnable example.
3. Write a short comparison explaining how the project complements JSON Schema, Zod, and front-end form libraries.
4. Ask engineers with configurable SaaS workflows for feedback on the API, not for stars.
5. Record concrete feedback and rejected feature requests in GitHub discussions or issues.
6. Publish a release only when its behavior and migration path are documented.

Useful success signals are a second independent domain, an external reproduction, a meaningful bug report, or a production pilot. Star count is a weak signal and should not drive API design.

## Explicit Non-Goals

- A no-code platform.
- A generic rules engine.
- An ORM or persistence abstraction.
- A tenant management system.
- A full JSON Schema implementation.
- A UI component library bundled into the core.
- Conditional visibility, cross-field rules, and plugin APIs before two domains require the same design.

## Definition of 1.0

Version `1.0` is justified only when all of the following are true:

- The core has been used by at least two distinct domain examples and one production or external pilot.
- Its schema and error contracts are documented, versioned, and tested.
- Installation and the quick start work from a clean environment.
- The package is independently publishable and its tarball contains no source application or private data.
- The maintainers can explain what the package does not solve as clearly as what it solves.
